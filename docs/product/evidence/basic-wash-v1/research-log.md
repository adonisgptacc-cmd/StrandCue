# Basic wash research log

What was searched for exact catalogue versions, what was found, and what is
missing. This pack is the research input for
`docs/superpowers/plans/2026-10-11-basic-wash-reviewed-content.md` Task 2. It is
evidence input only: nothing here approves content, and nothing here may be
promoted to a published bundle without the independent human review described in
`docs/runbooks/guidance-content-publication.md`.

## Blocking gap: the repository holds no catalogue version to research

**No candidate version is inventoried, because no catalogue version exists to
invent one from.**

- `supabase/migrations/20260924170000_shelf_catalogue.sql` creates the tables
  `public.brands`, `public.products`, `public.product_versions`,
  `public.product_claims`, `public.product_sources` and
  `public.product_verification_events`. It contains DDL, indexes, RLS policies
  and grants only. It inserts no rows.
- `supabase/migrations/20260924210000_tools_catalogue.sql` creates
  `public.tool_brands`, `public.tools`, `public.tool_versions`,
  `public.tool_claims`, `public.tool_sources` and
  `public.tool_verification_events`. It also contains no rows.
- No other file under `supabase/migrations/` inserts a row into any catalogue
  table. The `insert into` statements elsewhere in that directory are inside
  function bodies and write only passport, activity, shelf-owner, tool-owner,
  deletion, export and consent tables — never the catalogue.
- `supabase/drafts/` holds superseded, unapplied DDL and is deliberately not a
  resolution source: it was archived as an unverified milestone.
- No read-only catalogue export has been supplied to this repository. There is
  no approved `catalogue-snapshot.json` under this directory.

The result is that `product_versions` and `tool_versions` both resolve to zero
rows in every trusted local source. `inventory.json` therefore carries zero
rows, and `evidence-registry.json` carries zero records.

## Why nothing was written to fill the gap

A catalogue row is an identity claim: it says "this exact `versionId` is this
exact brand, name, variant or model, in this market, at this lifecycle, and this
source establishes that". None of that can be asserted without a real catalogue
row to resolve against and a real source that was actually read.

- Writing a plausible UUID, brand or product name here would manufacture an
  identity that no database row backs. Task 3's capability matrix and Task 4's
  publication gate resolve against these ids, so a fabricated row would
  eventually let an unreviewed, unverifiable product become reachable in the
  app.
- Reusing the `example.test` fixture identifiers from `tests/` is explicitly out
  of bounds: those rows exist to exercise RLS and the RPC cores, and they
  describe nothing that is sold in South Africa.
- Recording an evidence record without a real version would attach a claim to
  an identity that does not exist, which is the failure EV-01 and EV-02 exist to
  prevent.

So the honest pack is an empty pack, and this file is the record of why.

## Claim-scoped sources

None. No manufacturer directions, regulator notice, professional-body position,
peer-reviewed paper or independent test report was recorded, because there is no
exact version for such a source to be about. EV-02 requires a real URL, a real
publisher, a real retrieval date and a named human who read it; none of those
can be produced without a real source being read, and web research output is
evidence input, not approval.

## What unblocks this

Any **one** of the following, then the same validator run will accept a populated
pack:

1. **A reviewed seed migration.** Add the real ZA catalogue rows as a reviewed
   `supabase/migrations/*.sql` seed migration, inserting `brands`, `products`
   and `product_versions` (and the tool equivalents) with explicit `id` values.
   `scripts/validate-guidance-research.ts` reads `insert into public.<table>`
   statements out of every file in `supabase/migrations/` and joins
   brand → product → version (and tool brand → tool → tool version) to build the
   resolution set. Rows whose `id` is generated by `gen_random_uuid()` are
   skipped, because a generated id is not an identity anyone can reference.
2. **An approved read-only export.** Place an explicitly exported read-only
   snapshot at `docs/product/evidence/basic-wash-v1/catalogue-snapshot.json`:

   ```json
   {
     "snapshotId": "<name of the export>",
     "products": [
       {
         "versionId": "<exact product_versions.id>",
         "brand": "<brands.name>",
         "name": "<products.name>",
         "variantOrModel": "<product_versions.variant>",
         "market": "ZA",
         "lifecycle": "active"
       }
     ],
     "tools": []
   }
   ```

   Every field marked with `<...>` must be read out of a real catalogue, not
   typed from memory.

Either route then requires, for each inventoried version: the exact market and
formulation or model, the source that established that identity, and one
claim-scoped evidence record per claim with its URL, publisher, retrieval date,
limitations and a named author.

## What the validator refuses

`npm run validate:guidance-research` parses all three artifacts strictly and
exits non-zero on every one of these:

| Refusal | Why |
| --- | --- |
| an inventory id that resolves to no catalogue version | a manual Shelf or Tool entry with no catalogue match is not an identity (SH-02) |
| an inventory id that resolves to more than one catalogue version | an ambiguous identity must not be guessed at (SH-02, P-03) |
| a hand-written fixture id | test ids are not catalogue rows |
| the same `(kind, versionId)` listed twice | one version is inventoried once |
| a version the catalogue places outside ZA | the initial market is ZA (SH-02) |
| a formulation or model identity the catalogue does not carry | identity is established by the catalogue, not by the note taker (SH-02, SH-05) |
| brand, name, variant or model, lifecycle or source market that disagrees with the catalogue | a verified note is not a catalogue row (P-03, SH-05) |
| an evidence claim about a version the catalogue does not hold | a dangling claim covers nothing (EV-01) |
| a ZA claim about a version the catalogue places outside ZA | another market's evidence cannot support a ZA mapping (EV-01) |
| an evidence record marked `reviewed` | research may create draft content only; review is a human step outside automation (EV-04, EV-05) |
| an executable claim supported only by marketing | `T10` is marketing-only and never evidence of a capability |
| an empty inventory whose research log does not record the blocking gap | an unrecorded gap reads as an oversight |

The validator runs fully offline against files in this repository. It needs no
network access, no hosted Supabase, and no secrets.
